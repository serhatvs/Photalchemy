# Track A — Own-trained competitive card-game opponent

**Owner:** Serhat Yavuz · **Status:** P1 plan; no trained model or match dataset yet. This replaces the earlier photo-scene classification proposal in accordance with the gameplay requirement.

## Goal

Train a model that **understands the available cards and legal moves, observes the current battle, and chooses actions likely to beat the player**. The model must use attack, defense, stun and reflect strategically, considering current health/shields, timing, card strengths and future consequences. It must never see hidden player information or invent actions.

The **photo-to-card pipeline remains deterministic** using color statistics. It is not Track A. We must still build both deep course tracks: an **own-trained** action-choice model (A) and a **generative tool-calling enemy agent** with ≥20 evaluation scenarios (B).

## Observation / action contract

See `lib/features/battle/domain/enemy_policy.dart`:
- Public view: enemy/player health, shields, turn number, visible stun flags, last observed player card type, and current set of allowed enemy actions, including type/strength/effect descriptions.
- A real engine (Kadir) determines full turn state, cooldowns, stun, legal actions, event transitions and victory. Expand the view only by agreement.
- Model scores **only legal action IDs**. The battle engine validates again before applying. Player's hidden cards, deck order, photo EXIF and precise location are excluded.
- Trainable output target: **estimated win probability / action value for each legal action**. At inference, choose the highest-scoring allowed action; a legal deterministic baseline provides offline fallback.
- LLM Track B will consume the same legal action description and propose a tool call for the same validator. Keep comparison fair; models do not choose damage arbitrarily.

## Data collection without sensitive personal data

Generate **synthetic battle trajectories** from the deterministic combat simulator. Mix random, heuristic and varied competitive opponents; different starting hands, deck compositions, card strengths, player tactics, health states and seeds. State snapshots should include only information legal to observe. For each legal (state, action) pair, estimate value via bounded simulated rollouts/search or recorded eventual match outcomes; avoid training on answers generated by the same heuristic used as the only baseline.

- Reproducible seed, rules version, opponent version, match ID, trajectory/group ID, turn index and candidate action ID must be tracked. `ml/dataset_manifest_schema.csv` is a **header-only** suggested schema, not evidence of collected matches.
- Do not split individual turns from one match across training and testing; they are correlated. Group by **match/seed family or starting deck scenario**, keeping opponent setups disjoint as feasible.
- Log simulator version and reward definition. Reject illegal moves and detect loops. Generate no real photos, player location or private user content.
- Create deterministic, held-out challenge match sets, including unseen combinations of cards/opponents, so memorizing scripted matches does not inflate performance.

## Models and baselines (P2)

1. **Random legal** action baseline.
2. **Transparent heuristic** policy (e.g., immediate lethal attack when possible; otherwise defend against high incoming threat, consider stun when it prevents loss).
3. **Own-trained policy**, initially a small action-value ranking MLP: encode state and each candidate action as numeric features; train a scorer with supervised rollout targets or pairwise ranking. Apply legal-action mask. Evaluate actual win rate using the deterministic engine.
4. Optionally compare the generative Track B tool-calling opponent against the same opponents and seed sets, without counting an unmodified LLM as our trained Track A model.

Training must be real/reproducible; simply prompt-engineering an LLM or writing fixed card rules does NOT fulfill Track A. Record architecture, seed, split, hyperparameters, dataset provenance, validation and limitations in the model card. Confirm with instructor that simulation-based labels and learned action-value policy satisfy the own-trained track requirements.

## Evaluation: beating the player, not merely mimicking labels

**Primary metric: match win rate vs held-out, independently defined opponent policies** on fixed unseen battle seeds. Secondary: non-loss rate, reward margin, invalid action rate (goal: zero after validation), decision latency, per-state action ranking accuracy and win rate by card/deck matchup.

Use grouped cross-validation by match/scenario families for model selection, then a separate held-out challenge set. Compare with random and heuristic baselines on **paired matches with identical seeds and start states** where possible. Report a **95% confidence interval over independent matches or scenario groups**, not individual turns; explain small-sample limits. Inspect failure cases: threat recognition, not wasting stun, reflect timing, low-health defense and immediate lethal wins. Include strategic overfitting: does the model win only against the bots it trained against?

Do not claim any win rate, statistical significance or performance improvement before real simulator training/evaluation exists.

## Risks / decisions

- No deterministic battle engine exists yet: **cannot train a truthful policy or measure wins** until Kadir implements agreed rules and legal actions.
- If mechanics change mid-training, retrain and version matches; never train from invalid or hidden-state labels.
- Supervised rollouts may learn a weak teacher; verify improvement against independent opponents and human tests where possible.
- Choose client-side model vs secure backend based on latency/offline needs; keep paid-model keys off mobile clients.
